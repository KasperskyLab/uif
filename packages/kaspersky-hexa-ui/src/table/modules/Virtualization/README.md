# Виртуализация таблицы

Модуль отдаёт antd не всю таблицу, а только тот прямоугольник, который человек сейчас видит.
Ниже — разбор по файлам: что делает каждый и почему без него не обойтись.

Включается пропом `virtualization` (`true` или объект настроек), по умолчанию выключен.

## Зачем это нужно

Стори `Table/[DEV] Performance` — 1000 строк, 39 колонок, 100 строк на странице:

| | без окна | с окном |
|---|---:|---:|
| Узлов в DOM | 13 068 | **1 374** |
| Блокировка на маунте | 980 мс | **337 мс** |
| Отметить строку | 217 мс | **41 мс** |
| Тоггл в ячейке | 280 мс | **33 мс** |

Таблица без окна платит за каждую строку и каждую колонку, которые есть в данных, а не за те, что
видны. Сто строк на тридцать девять колонок — почти четыре тысячи ячеек, и каждая проходит через
обрезку, тултипы и styled-components.

На дереве разница перестаёт быть количественной. Корень с пятью тысячами детей раскрывался 1889 мс и
добавлял 85 460 узлов; с окном — 6 мс и 852 узла. Четыре таких корня без окна — миллион узлов и
вкладка, которую остаётся только закрыть.

## Идея

Срезать список, а дыры подпереть пустыми строками:

```
  данные             что уходит в rc-table          экран
 ┌────────┐         ┌─────────────────────┐
 │        │         │░░ распорка сверху ░░│
 │        │         ├─────────────────────┤        ┌──────────┐
 │  5000  │  ───▶   │   окно: ~25 строк   │  ───▶  │ видимое  │
 │ строк  │         ├─────────────────────┤        └──────────┘
 │        │         │░░ распорка снизу ░░░│
 └────────┘         └─────────────────────┘
```

Распорки — два обычных `<tr>` заданной высоты. Благодаря им таблица сохраняет настоящий рост, а
полоса прокрутки — настоящий диапазон. rc-table об этом не знает: ей отдали список из двадцати пяти
записей, и она честно нарисовала двадцать пять.

По горизонтали то же самое: колонки вне окна заменяются одной пустой колонкой суммарной ширины.

Главное решение — **внутри rc-table не переписано ничего**. Модуль стоит снаружи и подменяет только
то, что таблица получает на вход. Поэтому сортировка, фильтры, перетаскивание, группы и всё
остальное работают, не зная о нём.

## Место в системе

Таблица собирается из модулей-обёрток свёрткой, и порядок в массиве задаёт вложенность наоборот:
**чем раньше в списке, тем ближе к antd**.

```ts
// modules/index.tsx
const TableWithModules = modules.reduce((Component, module) => module(Component), Component)

export const tableModules: TableModule[] = [
  Virtualization,   // ← самый внутренний
  Groups,
  Pagination,
  SortingAndFilters,
  Reductions,
  // …
]
```

Виртуализация режет ровно то, что будет отрисовано, поэтому строки и колонки она должна увидеть
*после* пагинации, сортировки, фильтров, группировки и выбора колонок. Стой она выше, она нарезала
бы окно из данных, которые нижележащие модули потом переставят, и индексы разошлись бы.

## Что происходит за один рендер

Порядок здесь — настоящая последовательность.

1. **Понять, можно ли вообще.** Четыре запрета (см. «Где модуль отступает») проверяются до всего
   остального.
2. **Посчитать строки.** Для плоской таблицы это длина массива. Для дерева — длина плоского списка
   раскрытых строк: три корня с десятью тысячами открытых детей — это 10 003 строки, а не три.
3. **Найти, что скроллится.** Ближайший предок с настоящей прокруткой по каждой оси, иначе окно
   браузера. Плюс расстояние от верха скроллера до первой строки.
4. **Спросить у виртуализатора окно.** Два независимых виртуализатора tanstack, по одному на ось,
   отдают диапазон индексов, округлённый до блоков.
5. **Нарезать.** `rows.slice(start, end)` для плоской таблицы; для дерева — пересобрать поддерево
   так, чтобы видимые строки остались вложенными под своих родителей.
6. **Посчитать распорки.** Высота всего, что выше окна, и всего, что ниже, — из позиций, которые
   виртуализатор уже знает.
7. **Обернуть колонки.** Подменить `render` и `onCell`, чтобы индексы остались настоящими, и
   добавить `shouldCellUpdate`.
8. **Отдать antd.** Урезанные `dataSource` и `columns`, свой `components.body.wrapper`, свой
   `onRow` с ref для измерения.
9. **Измерить то, что смонтировалось.** После коммита — одной пачкой в микрозадаче, и уточнить
   оценку высоты для строк, которых никто ещё не видел.

## Файлы

### [`types.ts`](types.ts) — публичный контракт

Проп `virtualization` принимает `true` или объект. У каждого поля есть значение по умолчанию, и почти
все существуют потому, что у кого-то может оказаться таблица, не похожая на наши стори.

```ts
export type TableVirtualization = {
  rows?: boolean              // окно по строкам
  columns?: boolean           // окно по колонкам
  rowOverscan?: number        // запас строк за краем экрана
  columnOverscan?: number
  rowBlock?: number           // шаг, которым двигается окно
  columnBlock?: number
  estimatedRowHeight?: number // высота ещё не отрисованной строки
  getScrollElement?: () => VirtualScroller | null
}
```

### [`constants.ts`](constants.ts) — имена классов и ни одного импорта

Файл существует ради отсутствия зависимостей. `tableCss.ts` должен знать имя класса распорки, чтобы
не рисовать на ней разделитель строки и разлиновать её под высоту строки. Лежи эти имена в самом
модуле, таблица тянула бы за собой весь граф виртуализации ради двух строк.

### [`scrollers.ts`](scrollers.ts) — что скроллится и где начинается список

Виртуализатору нужно знать две вещи: у какого элемента спрашивать позицию прокрутки и на сколько
пикселей начало списка отстоит от начала этого элемента. У наших таблиц ответ не один: чаще всего
по вертикали скроллит сам документ (у таблицы нет `scroll.y`), а по горизонтали —
`.table-scrolling-wrapper`.

```ts
const scrollsOn = (element: HTMLElement, axis: 'x' | 'y'): boolean => {
  const style = getComputedStyle(element)
  const overflow = axis === 'x' ? style.overflowX : style.overflowY
  if (!CLIPS.includes(overflow)) return false

  return axis === 'x'
    ? element.scrollWidth > element.clientWidth
    : element.scrollHeight > element.clientHeight
}
```

> **Ловушка, ради которой написана вторая половина условия.** Если элементу задан
> `overflow-x: auto`, браузер делает вычисленный `overflow-y` тоже `auto`. Горизонтальная обёртка
> таблицы честно отвечает «я скроллюсь по вертикали», хотя её высота ничем не ограничена. Выбери мы
> её вертикальным скроллером — виртуализатор получил бы «экран» высотой во всю таблицу и не выкинул
> бы ни одной строки. Поэтому мало объявленного `overflow`, нужно реальное переполнение.

`getScrollMargin` считает смещение начала списка: когда скроллит страница, нулевая строка лежит не на
нулевом offset, а под тулбаром и шапкой. `getLeadingWidth` — то же по горизонтали: колонку выделения
antd подставляет сам, её нет в массиве, который мы режем, а ширину она занимает.

### [`useScrollContext.ts`](useScrollContext.ts) — кеш ответов про прокрутку

Обе функции выше читают геометрию — `getComputedStyle`, `scrollHeight`, `getBoundingClientRect`, — и
каждое чтение заставляет браузер пересчитать раскладку. Делать это на каждый рендер значит вернуть в
каждый шаг прокрутки пачку принудительных лэйаутов, то есть ровно то, от чего виртуализация
избавляет.

```ts
const context = useMemo<ScrollContext>(() => {
  if (!body) return EMPTY
  const vertical = override.current?.() ?? findScroller(body, 'y')
  return {
    vertical,
    horizontal: findScroller(body, 'x'),
    scrollMargin: getScrollMargin(body, vertical),
    leadingWidth: getLeadingWidth(body)
  }
}, [body, rowCount, revision])
```

Три зависимости — три реальные причины, по которым ответ может измениться: `body` (смена колонок
пересобирает DOM таблицы), `rowCount` (контейнер, который не переполнялся на пустой таблице, начинает
переполняться, когда приехали данные или раскрылся корень с тысячами детей) и `revision` (ресайз окна).

Отдельная хитрость — как получить `<tbody>`. Обёртку тела может задать Draggable, а это
функциональный компонент, которому ref не передашь. Поэтому ref вешается на нашу собственную верхнюю
распорку, а `<tbody>` берётся как её `parentElement`. Колбэк обязан быть стабильным: новая функция на
каждый рендер заставляла бы React отцеплять и перецеплять ref, а с ним перезапускать весь поиск.

### [`blockRange.ts`](blockRange.ts) — окно двигается ступеньками

По умолчанию окно tanstack сдвигается на строку, как только прокрутка пересекла границу строки.
Каждый сдвиг отдаёт таблице новый массив, а rc-table перерисовывает *все* строки окна — одного щелчка
колеса достаточно. На перфоманс-стори это давало медианный кадр 46 мс.

```ts
export const blockRangeExtractor = (blockSize: number) => (range: Range): number[] => {
  const first = Math.max(0, range.startIndex - range.overscan)
  const last = Math.min(range.count - 1, range.endIndex + range.overscan)
  const start = Math.max(0, Math.floor(first / blockSize) * blockSize)
  const end = Math.min(range.count - 1, Math.ceil((last + 1) / blockSize) * blockSize - 1)
  // …индексы от start до end
}
```

Пока экран не вышел за блок, набор строк не меняется вовсе, и большинство шагов прокрутки стоят ноль.

> **Что проверено и отвергнуто.** Держать больше строк *по ходу движения* выглядит очевидным
> лекарством от белых полос. Замер: два блока упреждения удвоили блокировку главного потока при
> прокрутке и почти не убрали полосы. Полоса живёт столько, сколько длится смена окна, а большее окно
> меняется дольше.

### [`useAxisVirtualizer.ts`](useAxisVirtualizer.ts) — один хук на обе оси

У tanstack два хука: `useVirtualizer` для элемента и `useWindowVirtualizer` для страницы. Нам не
подходит ни один по отдельности: таблица может скроллиться и так и так, и что именно — выясняется
только после монтирования. Внутри это один класс, разница в трёх адаптерах, поэтому хук подставляет
их сам.

На первом рендере мы ещё не знаем, что скроллится, а виртуализатор с нулевым экраном не выбирает ни
одной строки. Поэтому на первый кадр подставляется размер окна браузера (`initialRect`).

### [`useRowHeightEstimate.ts`](useRowHeightEstimate.ts) — высота строк, которых никто не видел

Полная высота таблицы — это «измеренные строки плюс оценка × все остальные». Ошибка в оценке
означает, что страница имеет неправильный рост: при прокрутке вниз она растёт под читателем, а
ползунок уезжает из-под курсора.

> **Самая коварная ошибка всей работы.** Первая версия брала размеры, которые виртуализатор сообщает
> про отрисованные строки. Но неизмеренная строка отдаётся с текущей оценкой — то есть среднее
> считалось по собственной догадке. На стори со строками по 103 px предположение ползло
> 55 → 64 → 76 → 88 → 101, и страница вырастала на 64%, пока читатель листал вниз. Лечится одним
> правилом: в выборку попадают только настоящие измерения из DOM.

`THRESHOLD = 8` — порог, ниже которого оценку не трогаем, иначе каждое мелкое колебание меняло бы
полную высоту списка, а вместе с ней и полосу прокрутки.

### [`useRowMeasure.ts`](useRowMeasure.ts) — измерение одной пачкой

Документированный способ сообщить высоту — передать `virtualizer.measureElement` прямо в ref. Но React
зовёт ref в фазе мутаций коммита, между вставками узлов: каждый `getBoundingClientRect` попадает после
записи в DOM и перед следующей, и браузер пересчитывает раскладку на каждую строку — 111 мс на
десятке шагов прокрутки, треть всей стоимости.

```ts
pending.current.push(node)
if (pending.current.length > 1) return   // пачка уже запланирована

queueMicrotask(() => {
  const nodes = pending.current
  pending.current = []
  if (!alive.current) return
  for (const element of nodes) {
    if (!element.isConnected) continue
    virtualizer.measureElement(element)
    // …и высоту в оценку
  }
})
```

Микрозадача выполняется после последней записи коммита и до отрисовки кадра: браузер раскладывает
страницу один раз на всю пачку, а размеры успевают попасть внутрь до кадра.

Две защиты — следствия реальных падений. `alive`: пачка выполнилась после того, как таблица
размонтировалась (setState на исчезнувшем компоненте — поймано на тесте InfiniteScroll).
`isConnected`: строка попала в очередь и вышла из окна до того, как очередь выполнилась.

### [`VirtualBody.tsx`](VirtualBody.tsx) — пустые строки, которые держат рост

Подменяется `components.body.wrapper`, а внутрь ставятся две пустые строки: над окном и под ним.

Компонент определён на уровне модуля и всё берёт из контекста — это обязательно. rc-table
перерисовывает *каждую ячейку*, когда меняется идентичность любого компонента в `components`, так что
обёртка, созданная внутри рендера, перестраивала бы таблицу на каждом шаге прокрутки. А через пропсы
живые значения не передать: `Body` у rc-table мемоизирован, и изменившийся паддинг до обёртки не
дошёл бы.

Верхняя распорка рендерится всегда, даже с нулевой высотой: через неё мы добираемся до `<tbody>`.
`Base` хранит обёртку, на место которой мы встали (например, sortable-обёртку Draggable).

> **Почему у ячейки распорки `colSpan` с запасом.** Таблица показывает *свой* фон в любой клетке
> сетки, которую не накрыла ячейка. Одна ячейка без `colSpan` шириной в первую колонку — и линовка
> распорки обрывалась на границе первой колонки. Замерено: избыточный `colSpan` при фиксированной
> раскладке не меняет ни ширину таблицы, ни `colgroup`, ни ширину прокрутки.

Линовка нужна вот зачем: распорку почти никогда не видно, но в момент, когда читатель обогнал
отрисовку, она единственное, что есть на экране. Без неё это читается как дыра; разлинованная под шаг
строки — как строки, которые сейчас приедут.

### [`columns.ts`](columns.ts) — окно по горизонтали

Горизонтальное окно может расставить только те колонки, ширину которых можно узнать, не отрисовывая
их. Поэтому у каждой видимой колонки нужна числовая `width`.

Требование бесплатное: `resizingMode: 'scroll'` даёт ширину каждой колонке — и это ровно тот режим, в
котором оказывается таблица шире контейнера. `'last'` и `'max'` намеренно оставляют одну колонку
без ширины, чтобы она тянулась, — но такая таблица помещается на экран, и выкидывать из неё нечего.

`windowColumns` заменяет каждый пробег колонок вне окна одной пустой колонкой той же суммарной ширины
и на том же месте. Никогда не выкидываются служебные колонки antd (выделение, раскрытие) и
закреплённые (`fixed`) — выкинутая закреплённая колонка уехала бы со своего места. Скрытые колонки
проходят насквозь нетронутыми: `Table.tsx` отфильтрует их сам, а выбрось мы их здесь — изменится то,
что сообщает `onPatchedColumnsChange`.

### [`cellMemo.ts`](cellMemo.ts) — настоящие индексы и `shouldCellUpdate`

**Индексы.** rc-table нумерует строки внутри того массива, который ей дали. Мы даём срез — значит,
любой колбэк с индексом увидел бы номер внутри окна: колонка «номер строки» начинала бы заново с
единицы после прокрутки, зебра переворачивалась бы, а `onRow`, который ищет запись по индексу, брал
бы не ту.

```ts
export type RowPositions = {
  offset: number
  renderIndexOf?: Map<unknown, number>  // что видит column.render — номер среди братьев
  flatIndexOf?: Map<unknown, number>    // что видят onRow и rowClassName — место в списке
}
```

Плоской таблице хватает одного смещения, карты она не строит вовсе. Дереву нужен номер на строку:
`column.render` получает индекс среди братьев, а окно заменяет детям родителя на те несколько, что
видны.

**`shouldCellUpdate`** — главный рычаг на стоимость прокрутки:

```ts
shouldCellUpdate: column.shouldCellUpdate ?? ((record, previous) => record !== previous)
```

rc-table заворачивает ячейку в `React.memo`, но без `shouldCellUpdate` сравнение падает на
поверхностное сравнение пропсов, а `onCell` отдаёт свежий объект на каждый рендер — сравнение не
проходит никогда. Замерено: без этой строки вертикальная прокрутка теряет на 47% больше кадров,
горизонтальная — на 15%.

> **Почему здесь нет кеша ячеек.** Раньше модуль ещё и запоминал, во что отрисовалась каждая ячейка, и
> отдавал тот же React-элемент. Замер показал ровно ноль на обеих осях: вертикаль 1014 → 1017 мс
> потерянных кадров, горизонталь 1433 → 1437. Причина в устройстве rc-table: `column.render`
> вызывается внутри `Cell`, а `MemoCell` бракует ячейку раньше, если запись та же. Кеш мог сработать
> только для той же записи — то есть ровно тогда, когда `render` уже не вызывался. А стоил он дорого:
> закешированный элемент держит фибер, фибер держит DOM, и безлимитная версия оставляла шесть тысяч
> оторванных узлов; ключ по `column.key` заставлял ячейки рисовать содержимое друг друга. Удалён вместе
> с опцией `memoizeCells`.

### [`tree.ts`](tree.ts) — окно из дерева без потери вложенности

`flattenRows` повторяет обход, который rc-table делает в `useFlattenRecords`: спускается только в
раскрытых родителей. Результат — плоский список того, что реально на экране, и его длина идёт в
виртуализатор.

`buildTreeWindow` собирает обратно самое маленькое дерево, которое отрисует ровно строки окна.
Копируются **только раскрытые родители**, и только ради того, чтобы подменить им список детей:

```ts
const rendered = expanded ? { ...record, [childrenColumnName]: [] } : record
```

Каждый лист и каждый свёрнутый родитель проходит насквозь *тем же объектом*, поэтому
`shouldCellUpdate` продолжает работать для строк, которые и составляют основную массу дерева.

Две поправки, без которых дерево ведёт себя неправильно. Строка, чей родитель выше окна, должна
остаться вложенной — поэтому предки отрисовываются тоже, а их высота вычитается из верхней распорки.
И если на нижней границе окна оказался раскрытый родитель, окно расширяется на строку: иначе он
остался бы без детей и без контрола, которым его сворачивают.

### [`useExpandedKeys.ts`](useExpandedKeys.ts) — управление раскрытием

Чтобы нарезать дерево, надо знать, что в нём раскрыто, а antd держит это у себя, если никто не
управляет снаружи. Поэтому для дерева управляет модуль: держит ключи, когда их не держит никто,
отдаёт их вниз и сообщает наверх обо всех изменениях. Тот, кто уже управляет `expandedRowKeys` сам,
управления не теряет — его значение выигрывает, его колбэк по-прежнему вызывается.

### [`Virtualization.tsx`](Virtualization.tsx) — сборка

Файл читается сверху вниз как последовательность решений, а в конце один `return`, где подменяются
пропсы:

```tsx
<VirtualBodyProvider value={bodyValue}>
  <Component
    {...props}
    dataSource={windowedRows}
    columns={windowedColumns}
    components={components}
    onRow={rowsOn ? onRow : props.onRow}
    rowClassName={rowClassName}
    expandable={isTree && rowsOn ? expansion.expandable : props.expandable}
    tableLayout={columnsOn ? 'fixed' : props.tableLayout}
  />
</VirtualBodyProvider>
```

`tableLayout: 'fixed'` обязателен при оконных колонках, иначе ширины считались бы по тому, какие
ячейки сейчас отрисованы, и колонки прыгали бы на каждом шаге горизонтальной прокрутки.

`onRow` возвращает объект, который React разворачивает в `createElement`, поэтому через него проходят
и `ref` (измерение высоты), и `data-index` (по нему виртуализатор понимает, чья это строка). Ref обязан
быть стабильным.

`positions` лежит в ref и пишется прямо во время нашего рендера, до того как отрендерится поддерево
таблицы, поэтому любой колбэк ниже видит смещение того среза, который рисуется сейчас. Обёртка колонок
создаётся один раз на идентичность массива колонок: оборачивай мы заново на каждый шаг прокрутки,
rc-table перестраивала бы все ячейки.

Первый кадр ограничен намеренно. Пока виртуализатор ничего не измерил, он отдаёт пустой список, и
откатиться в этот момент на «рисуем всё» значило бы смонтировать целиком таблицу, которая существует
именно потому, что целиком не монтируется. Запасной вариант — четыре блока:
`Math.min(rowCount, rowBlock * 4) - 1`. На дереве в двадцать тысяч строк это разница между
восемьюстами узлами и миллионом.

## Где модуль отступает

| условие | почему |
|---|---|
| `expandedRowRender` | одна запись рисует две строки, и отрисованное перестаёт совпадать с посчитанным |
| функция в `components.body`, свой `components.table` | телом владеет другая реализация — старая виртуализация `useVT` делает и то и другое, её включает `pagination.virtualInfiniteScroll` |
| `rowSelection` без `builtInRowSelection` | antd выводит всё о выделении из тех строк, что ему дали, и окно принимает за всю таблицу: отметка сбрасывала уехавшие строки, «выделить все» означало 30 строк из 5000, shift-клик через границу не выделял ничего. Строки остаются целыми, **колонки оконятся по-прежнему** |
| `stickyHeader` — только для колонок | липкая шапка сопоставляет свои `<th>` с массивом колонок один к одному |

## Известное ограничение: горизонтальная прокрутка

Любой сдвиг окна — по строкам или по колонкам — отдаёт rc-table новый массив, и она пересоздаёт
элементы **всех** ячеек окна. Каждая ячейка проходит через `WrappedCell`: он не мемоизирован и читает
`HoverContext`, и только после него `MemoCell` бракует ячейку по `shouldCellUpdate`. Эта нижняя граница
стоимости живёт внутри rc-table.

На горизонтали это заметно. Прод-сборка, Performance, `stickyHeader` не задан (значит, колонки
оконятся):

| | худший кадр | кадров дольше 32 мс | потеряно на кадрах |
|---|---:|---:|---:|
| без виртуализации | 113 мс | 1 | 96 мс |
| строки и колонки | 259 мс | 14 | 789 мс |

Размеры блоков только перекладывают стоимость между осями (дев-сборка, потеряно на кадрах):

| конфигурация | горизонталь | вертикаль |
|---|---:|---:|
| без виртуализации | 97 | 0 |
| только строки | 97 | 2317 |
| `rowBlock` 5, `columnBlock` 2 (по умолчанию) | 1367 | 1014 |
| `columnBlock` 4 | 832 | 1317 |
| `rowBlock` 10, `columnBlock` 4 | 1081 | 894 |

Окно колонок делает каждое окно строк уже, поэтому вертикаль дешевле; зато каждое пересечение
колонок пересоздаёт всё окно, поэтому горизонталь дороже. Таблице, которую вбок прокручивают часто,
можно отключить окно колонок: `virtualization={{ columns: false }}`.

И общее: на странице в сто строк виртуализация делает саму прокрутку дороже, чем без неё, — её выигрыш
в маунте и в интеракциях. Незаменима она там, где строк тысячи или где дерево.

## Ловушки, найденные по дороге

**Конфиг `expandable` отставал на рендер.** `useExpandColumnName` держал его в состоянии и переписывал
из эффекта. При сворачивании этот отстающий кадр ещё считал корень раскрытым и строил все пять тысяч
детей, чтобы тут же их убрать: 1698 мс синхронно в обработчике. Теперь значение считается в `useMemo`
— 8 мс. Раскрытие при этом было дешёвым, что и сбивало с толку: отстающий кадр там считает корень
ещё свёрнутым.

**Storybook морозил вкладку на десять минут.** `jsxDecorator` из `@storybook/react` рисует панель кода,
прогоняя `react-element-to-jsx-string` по отрисованному элементу стори вместе со всеми пропсами.
`dataSource` из 20 004 записей выписывался в строку 631 секунду, одной задачей. Поэтому стори модуля
монтируют компонент (`<TreeDemo {...args} />`) и объявляют `docs.source.type: 'code'` — каждого из этих
двух средств хватает одного.

**Метрика, которая измеряла Playwright.** `click()` ждёт, пока элемент станет стабильным и видимым, и
это ожидание попадает в стенные часы любого, кто меряет вокруг вызова: 916 против 584 мс вместо
настоящих 247 и 35. Интеракции надо мерить диспетчеризацией события изнутри страницы.

## Как проверять

`npm run test:virtual` прогоняет собственные наборы таблицы второй раз с принудительно включённой
виртуализацией — так модуль держат на поведении таблицы без него. Собственные тесты модуля —
`src/table/__tests__/Virtualization*.test.*`.

Глазами: `Table/[DEV]/Virtualization` (5000 строк × 30 колонок, переключатель `virtualization` в
контролах) и `Table/[DEV]/Virtualization/Tree` (четыре корня по 5000 детей). С выключенным
переключателем обе стори отказываются рисовать таблицу и показывают предупреждение.
