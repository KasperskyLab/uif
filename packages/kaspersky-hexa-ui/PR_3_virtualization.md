# Виртуализация таблицы

Коммит: `feat: render only the rows and columns the reader can see`

Таблица платит за каждую строку и каждую колонку, которые существуют в данных, а не за те, что
видны. Сто строк на тридцать девять колонок — почти четыре тысячи ячеек, и каждая проходит через
обрезку, тултипы и styled-components, пока человек смотрит на два десятка строк.

Модуль отдаёт antd окно вместо всей таблицы: `dataSource` урезан до строк в поле зрения,
`columns` — до колонок в поле зрения, а дыры держат пустые строки и одна пустая колонка той же
суммарной ширины. Внутри `rc-table` не тронуто ничего, поэтому сортировка, фильтры, группировка,
перетаскивание и всё остальное продолжают работать, не зная о нём.

**Разбор по файлам — что делает каждый и почему без него не обойтись:**
[`src/table/modules/Virtualization/README.md`](src/table/modules/Virtualization/README.md)

## Замеры

Стори `Table/[DEV] Performance`, 1000 строк × 39 колонок, 100 строк на странице, Chrome,
1600×1000. Медиана трёх прогонов; интеракции меряются диспетчеризацией события внутри страницы,
а не через `click()` драйвера — иначе в стенные часы попадает его собственное ожидание
доступности элемента.

| | без окна | с окном |
|---|---:|---:|
| Узлов в DOM | 13 068 | **1 374** |
| Строк в DOM | 100 | **15** |
| Блокировка на маунте | 980 мс | **337 мс** |
| Отметить строку | 217 мс | **41 мс** |
| Переключить тоггл в ячейке | 280 мс | **33 мс** |
| Выделить все | 75 мс | **8 мс** |

Дерево (4 корня по 5000 детей, стори `Table/[DEV]/Virtualization/Tree`):

| | без окна | с окном |
|---|---:|---:|
| Раскрыть корень | 1889 мс | **6 мс** |

Все четыре корня раскрыты — это 20 004 строки — ноль длинных задач на каждом шаге и максимум
1076 узлов в документе.

## Что сделано

### 1. Окно по строкам и по колонкам

Два независимых виртуализатора `@tanstack/react-virtual`, по одному на ось. Края окна
округляются до блоков, поэтому набор отрисованных строк меняется ступеньками, а не на каждую
строку: без этого один щелчок колеса перерисовывал всё окно, и медианный кадр был 46 мс.

Дыры закрывают пустые `<tr>` заданной высоты и колонка-распорка суммарной ширины — таблица
сохраняет настоящий рост, обе полосы прокрутки сохраняют диапазон.

### 2. Динамическая высота строк

Ни одна высота не объявляется заранее: каждая смонтированная строка сообщает свою. Измерения
собираются в пачку и выполняются из микрозадачи — ref-колбэк React зовёт между вставками узлов,
поэтому измерение прямо в нём заставляет браузер раскладывать страницу на каждую строку
(измерено: 111 мс на десятке шагов прокрутки, треть всей стоимости).

Высота для ещё не отрисованных строк усредняется **только по настоящим измерениям**. Первая
версия усредняла размеры, которые виртуализатор сообщает про отрисованные строки, — но
неизмеренная строка отдаётся с текущей догадкой, и среднее училось само на себе: на стори со
строками по 103 px предположение ползло 55 → 64 → 76 → 88 → 101, а страница вырастала на 64%
пока читатель листал вниз.

### 3. Деревья

Окно режется из плоского списка раскрытых строк, а не из массива верхнего уровня: три корня с
десятью тысячами открытых детей — это 10 003 строки, а не три. Оконные строки собираются
обратно в минимальное поддерево; копируются только раскрытые родители, чтобы подменить им
список детей, а каждый лист и каждый свёрнутый родитель проходят насквозь тем же самым
объектом — иначе перестал бы работать `shouldCellUpdate`.

### 4. `shouldCellUpdate`

rc-table заворачивает ячейку в `React.memo`, но без `shouldCellUpdate` сравнение падает на
поверхностное сравнение пропсов, а `onCell` отдаёт свежий объект на каждый рендер — ячейка не
пропускается никогда. Модуль ставит `record !== previous` колонкам, у которых нет своего правила.
Без этой строки вертикальная прокрутка теряет на 47% больше кадров, горизонтальная — на 15%.

Кеша отрисованных ячеек в модуле нет, и это измерено: rc-table вызывает `column.render` внутри
`Cell`, а `MemoCell` бракует ячейку раньше, так что кеш мог сработать только там, где `render` и так
не вызывался. Ноль на обеих осях.

### 5. Инфинити-скролл

Работает как прежде, отдельной поддержки не потребовалось: модуль стоит под пагинацией и видит
уже дозагруженные строки.

## Где модуль отступает

Выключен по умолчанию, включается пропом `virtualization`. Отступает там, где не может быть
корректным:

| условие | почему |
|---|---|
| `expandedRowRender` | одна запись рисует две строки, и отрисованное перестаёт совпадать с посчитанным |
| функция в `components.body`, свой `components.table` | телом владеет другая реализация — старая виртуализация `useVT` делает и то, и другое |
| `rowSelection` без `builtInRowSelection` | antd выводит всё о выделении из тех строк, что ему дали; окно он принимает за всю таблицу. **Колонки при этом оконятся по-прежнему** |
| `stickyHeader` — только для колонок | липкая шапка сопоставляет свои `<th>` с массивом колонок один к одному |

Про выделение подробнее, потому что это единственное ограничение, которое видно потребителю.
Замерено на выключенном фиксе: отметка строки сбрасывала все уехавшие, «выделить все» означало
30 строк из 5000, shift-клик через границу окна не выделял ничего. У встроенного выделения этих
проблем нет по устройству — оно ведёт свой список и работает по полным данным. Строки без него
не оконятся, и в дев-режиме таблица пишет в консоль, почему.

Колонкам дополнительно нужна числовая `width` у каждой видимой колонки. Это бесплатное
требование: `resizingMode: 'scroll'` даёт ширину всем, и это ровно тот режим, в котором
оказывается таблица шире контейнера.

## Два фикса, найденных по дороге

- **`useExpandColumnName` отставал на рендер.** Держал конфиг в состоянии и переписывал его из
  эффекта, поэтому таблица всегда была на кадр позади того, что ей сказали. При сворачивании
  этот отстающий кадр всё ещё считал корень раскрытым и строил все пять тысяч детей, чтобы тут
  же их убрать: 1698 мс заблокированного потока на клик, который должен стоить ноль. Теперь
  значение считается в `useMemo` во время рендера. Есть тест, который считает построенные
  строки: без фикса 1988 при пороге 10.
- **Принудительная вёрстка в `Table.tsx`.** `ResizeObserver` пересчитывал всё и при изменении
  высоты, хотя обе операции зависят только от ширины и обе стоят принудительной раскладки. А
  `previewTableWidth` читался из DOM прямо во время рендера, и ничего его не задавало до первого
  ресайза окна — то есть каждый рендер таблицы заставлял браузер раскладывать страницу заново.

## Тесты

`npm run test:virtual` прогоняет собственные наборы таблицы **второй раз** с принудительно
включённой виртуализацией — так модуль держат на поведении таблицы без него. 640 тестов.

Плюс собственные наборы на окно строк, окно колонок, деревья и правило про выделение.

По пакету: **1358 тестов зелёные** в обычном режиме, **640** в режиме принудительной
виртуализации, `tsc` без ошибок, eslint без ошибок.

## Что стоит посмотреть глазами

Стори `Table/[DEV]/Virtualization` — 5000 строк × 30 колонок, переключатель `virtualization` в
контролах, чтобы сравнить. И `Table/[DEV]/Virtualization/Tree` — четыре корня по 5000 детей.

С выключенным переключателем обе стори отказываются рисовать таблицу и показывают предупреждение:
смонтировать их целиком — это десятки тысяч ячеек и вкладка, которую остаётся закрыть.
